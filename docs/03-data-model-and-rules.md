# 03 数据模型与业务规则

版本：v1.0 ｜ 日期：2026-10-01

## 1. 约定

- 金额：`*_cents` INTEGER，单位分，带符号字段用 `signed_cents`（网点视角：收为正、支为负）。
- 日期：`YYYY-MM-DD`，上海时区自然日；时间：`YYYY-MM-DD HH:MM:SS`。
- 主键：流水 `flow_id = {source}:{source_ref}`。
- 枚举：大写英文常量，展示层翻译为中文。

### 2.1 `flows`

| 字段 | 说明 |
| --- | --- |
| `flow_id` `source` `source_ref` | 来源与主键 |
| `account_code` | 统一账户码 |
| `biz_date` `biz_time` | 业务日期/时间 |
| `direction` | `IN` / `OUT` |
| `amount_cents` | 绝对值金额（分） |
| `balance_after_cents` | 交易后余额（来源提供时） |
| `counterparty` | 对方（脱敏后） |

| `summary` | 摘要/备注（单行，≤200 字） |
| `initiator` | 发起人（中天提现等） |
| `status_text` | 来源状态（审核/入账/收付），仅展示 |
| `raw_json` | 来源原始记录（本地私有库，用于重映射；不进入报表） |
| `raw_hash` `first_seen` `last_seen` `removed` | 变更检测；来源中消失的记录标记 `removed=1` |

### 2.2 `daily_results.payload`（JSON）

日结果是报表、预警、分析的唯一输入，结构见 `src/cashrecon/engine/result.py`，主要字段：

- `sources`：各来源采集状态与行数
- `accounts[]`：期初、收入、支出、划转入/出、期末（计算）、报告期末、独立对照余额、差额、核对状态
- `profit`：现金口径收入/成本按科目、经营利润、未分类金额
- `bill_profit`：账单口径对照
- `transfers` / `withdrawals`：内部划转、充值、提现及其匹配情况
- `recon`：重复/划转/正常/待核 笔数与金额，待核清单
- `position`：现金头寸合计（区分已独立核对与未核对）
- `data_status`：`OK` / `PARTIAL` / `MISSING` 与缺失来源

## 4. 对账规则

### 4.1 中天利润与余额
- 中天当日经营收支 = `ZT_SUMMARY` 科目分项中，统一科目计入利润的分项之和；划转类分项（充值/提现/中通支付钱包/代收）列入资金去向。
- 余额等式：`期初 + 当日发生额 = 期末`（门户汇总）；`ZT_FLOW` 逐笔合计与门户发生额的差异作为“逐笔采集完整性”指标。

### 4.2 重复识别（日记账 ↔ 自动采集）
- 范围：配置中标记为“自动采集”的账户（对公卡、店主支付宝、工行卡）上的日记账记录。
- 候选：同账户、同方向、金额相等、日期差 ≤ 2 天。
- 分组配对：同（账户、方向、金额）的两侧记录各按时间排序，按日期最近原则一一配对；若存在多个等距候选则整组进入待核。
- 结果：自动采集记录为主记录；日记账记录标 `DUPLICATE`，其科目描述（若更具体）用于主记录分类。
- 自动采集账户上未能配对的日记账记录 → 待核（可能是登记错误、测试数据、余额修改）。

### 4.3 内部划转 / 充值 / 提现 / 余额宝
- 内部划转：两个本网点账户一出一入、金额相等（或差额 ≤ max(5 元, 0.6%) 视为含手续费）、时间差 ≤ 1 天。
- 中天充值：自动采集账户付中通总部（或日记账“中天余额充值”）↔ 中天“中通支付充值”，同日或次日金额相等；**匹配不上的付总部款项按购买单号/物料计入面单成本**。
- 中天预付款提现（线下提现）：承包区/业务员劳务费，计入人工成本；发起人账号通过系统员工信息查姓名。如某发起人实为转入本网点账户，在配置 `withdraw_initiators` 指定账户后按划转匹配。
- 余额宝（`[[sweeps]]` 配置）：支付宝余额“余额自动转入”/“转出到余额”、以及店主从余额宝汇总转给出纳的款项（按 `owner_hints` 识别）记为“支付宝↔余额宝往来”，不计利润。默认不统计余额宝余额；如需统计，可配置 `fund` 指向一个 `collection = "derived"` 的虚拟账户，系统以首次人工录入余额为起点推算。
- 店主个人收支：对方或摘要含店主姓名（`site.owner_names`）、且无法匹配到本网点账户的划转，记为“店主个人收支”，不计利润、不待核。
- 单边划转（另一端不在系统内）：列入待核“对方账户不明”。

### 4.5 业务期间（权责）
每笔流水的业务期间按优先级确定：人工指定 > 日记账“业务发生时间”（与登记日不同时才视为已填写）> 对应日记账的业务发生时间（银行流水与日记账去重后继承）> 工资类规则（`[accrual]`：人工/驿站派费、≥5,000 元、每月 15–28 日支付 → 上月）> 收付日。
经营利润按业务期间逐日平均分摊；晚到的登记会自动重算其覆盖的历史日期（日报文件重新生成，不重复发送）。

### 4.4 逐账户余额核对
| 账户类型 | 计算期末 | 独立对照 |
| --- | --- | --- |
| 中天主账户 | 门户汇总期末 | 逐笔流水合计（完整性） |
| 对公卡 / 工行卡 | 前日期末 + 当日短信收支 | 当日最后一条短信余额；门户日记账账户期末 |
| 店主支付宝 | 前日期末 + 当日账务收支 | 官方账务明细余额 |
| 手工账户（支付宝/微信/建行） | 门户日记账账户汇总 | 人工录入实际余额（周末） |
- 状态：`MATCH`（|差额| < 0.01）、`DIFF`（差额并给原因候选）、`NO_REF`（无独立对照，展示为“仅账面”）、`MISSING`（来源缺失）。

## 5. 预警规则

见 [01 §FR-8](01-requirements.md)。实现约定：
- 幂等键 `rule:biz_date[:object]`；冷却期按规则配置；同一预警状态未变化时不重复发送。
- 预警进入日报“需要处理”区块；高/中级同时邮件发送（日报邮件合并发送，紧急预警单独发送）。

## 6. 数据完整性

每来源每日：采集状态、行数、与近 14 天同星期中位数之比、最新记录时间。
`data_status`：任一必需来源失败 → `MISSING`；行数异常或非必需来源失败 → `PARTIAL`；否则 `OK`。
